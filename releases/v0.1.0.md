# ExecBound 0.1.0

The first release of self-hosted ExecBound Community: the gateway and its console, the Python client, the provider protocol, the connectors, the examples and the integrations, published as one signed image.

ExecBound sits between an AI agent and the systems it acts on, and decides outside the model whether each action may run. The agent asks over MCP or HTTP. ExecBound resolves the request to one canonical action and one target against trusted inventory, applies deterministic Cedar policy and shared impact limits, asks a named person when a rule says to, and only then lets the action run.

## What is in it

- **Three placements.** Execute holds the provider credential and dispatches a governed action itself. Gate issues a plan-bound grant to an external executor. Monitor receives activity without granting execution authority.
- **Decisions outside the model.** Policy, trusted context and limits decide. An unknown action, a mismatched target or missing context fails closed.
- **Approvals.** A rule can hold a request for a named approver. An approval is scoped to the exact request, expires, and is consumed once.
- **Shared impact limits.** Limits count the targets affected across agents, runs and protocols within the scope you configure, and reservations are atomic.
- **A record you can replay.** Every decision is appended to the workspace's audit chain with its evidence. An exported history replays offline without acting on anything, and the chain can be verified.
- **The console.** Home, Activity, approvals, policies and rules, agent connections, people and Spaces, and monitoring.
- **Integrations, each at its own evidence level:** Tines instrumentation and collection, the external execution checkpoint, Arcade hooks, and Scout's Microsoft Entra inventory and audit source. [Integrations](https://github.com/ExecBound/execbound/blob/v0.1.0/docs/INTEGRATIONS.md) says which path is tested and how far.

## Install

The image is `ghcr.io/execbound/execbound:0.1.0`, built for `linux/amd64`. Its digest and the command that verifies its signature follow these notes.

1. Verify the signature, as [Releases](https://github.com/ExecBound/execbound/blob/v0.1.0/docs/RELEASE.md#verify-an-image-before-you-run-it) describes, and note the digest it names.
2. Follow [Install on one host](https://github.com/ExecBound/execbound/blob/v0.1.0/docs/INSTALL.md), using `ghcr.io/execbound/execbound@sha256:<digest>` wherever it says `execbound:community`. The guide still describes building the image yourself, which also works.

## Upgrading

This is the first release, so there is nothing to upgrade from. On a new installation, `execbound quickstart` applies the database schema when it sets the deployment up.

## What it does not do

- It supports one canonical target per action and fixed provider operations. There is no generic HTTP passthrough, no batch mutation, no automatic resend of an uncertain operation, and no approval flag the agent can supply.
- Gate and Monitor do not stop a caller that uses a separate credential outside ExecBound.
- Tenant row-level security does not contain an attacker who obtains arbitrary SQL access with the runtime credential.
- A fresh installation runs against two mock providers. Read [Deployment](https://github.com/ExecBound/execbound/blob/v0.1.0/docs/DEPLOYMENT.md) before anything real depends on it.
- No package is published to PyPI. The Python client is installed from the repository with `pipx`.
- Only the latest release is supported, and security fixes are made in it alone.

The [threat model](https://github.com/ExecBound/execbound/blob/v0.1.0/docs/THREAT_MODEL.md) lists each threat with its mitigation, the code that enforces it, the test that exercises it and its status.
