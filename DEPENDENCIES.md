# Runtime dependencies

Every Python distribution a release installs, its license, and why it is here.
`console/DEPENDENCIES.md` is the
same document for the npm tree; this is the Python half, and the two are checked the same
way.

`scripts/python_sbom.py` reads the set from `uv.lock`, walking the project's own
dependencies and the `showcase` group the image installs beside them through the extras the
lock resolved, and reads each license from the distribution's **installed metadata**,
because that is the copy that ships. `tests/test_python_dependencies.py` holds this document
to both, and the `verify` job runs the script, so a new distribution, a changed license or a
stale line here is a reviewed change and never a side effect of a lock.

Versions are deliberately not in the table. They are in the CycloneDX SBOM the script writes
beside the release provenance, exactly and with the lockfile's own digests, and the license
check reads the installed metadata rather than a version, so repeating them here would add a
line to review on every lock without adding anything to review.

This document records which license each distribution carries and why it is here. [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md) reproduces the license texts and notices those licenses require a release to carry, generated by `scripts/third_party_notices.py` from the same runtime set, the Rust crates compiled into `cedarpy` and the console's production packages, and checked current by `verify`.

Development distributions are not inventoried. They ship in nothing: not in the wheel, not
in the image, not in the client. `pytest`, `ruff`, `mypy`, `playwright`, `hypothesis` and
`aiosmtpd` are the direct ones, and none of them is a runtime dependency of anything here.

## License exceptions

A distribution whose license is outside the allowlist is named here with its obligation, or
the check fails. The allowlist is MIT, the BSD family, the PSF license,
Apache-2.0, and the dedications that oblige less. Strong copyleft is refused even with an
entry here: this tree has no GPL-only dependency, and an exception is for
a notice a distributor can ship, not for a license decision about the combined work.

- `psycopg` and `psycopg-binary`: LGPL-3.0-only. Imported unmodified as a library, which is
  the case the LGPL's linking exception is for. What a distributor owes is the license text
  and a pointer to upstream source; `THIRD_PARTY_NOTICES.md` carries both.
  Nothing here modifies the driver, and the image installs the
  published wheel.
- `certifi`: MPL-2.0. File-level copyleft on certifi's own files, which nothing here
  modifies or redistributes separately. Notice only. It is also the one obligation that
  reaches the Apache-2.0 client, because the client's own dependency closure includes it
  through `httpx`; MPL-2.0 and Apache-2.0 coexist in one distribution as long as certifi's
  files stay unmodified, which they are.

## Release-age exceptions

Every ecosystem waits seven days before a version is proposed, so a compromised release has a
week to be noticed before it can land. A version pinned sooner is named here with the reason,
and needs nothing further once it is seven days old.

- `certifi` 2026.10.19, pinned on 21 October 2026, a day after its release. It removes root
  certificates whose intermediates' keys were compromised (GHSA-6q48-6c7w-9gw2, critical),
  which the image's outbound TLS trusted, and a critical trust-store fix outweighs the week.
  It is seven days old on 27 October 2026.

## Licenses the installed metadata does not declare

Some distributions supply no SPDX expression this script will read. Each was read by hand,
from the file named below, and the license in the table is what that file says. An entry
here is what lets the check accept a license it could not read for itself.

- `qrcode`: BSD-3-Clause AND MIT. Its legacy metadata says only `BSD`; the installed
  `qrcode-8.2.dist-info/licenses/LICENSE` includes the three-clause BSD license and the
  retained MIT notice for the original QR implementation. Both notices ship unmodified.
- `colorama`: BSD-3-Clause. Its installed `dist-info/licenses/LICENSE.txt` includes
  redistribution, binary notice and non-endorsement clauses; metadata names only the BSD family.
- `pyopenssl`: Apache-2.0. Its legacy metadata uses prose; installed `dist-info/licenses/LICENSE`
  is the full Apache 2.0 text.
- `cedarpy`: Apache-2.0. Its PyPI metadata carries no license field at all, and the wheel
  ships the full Apache 2.0 text at `cedarpy-<version>.dist-info/licenses/LICENSE`. The same
  wheel ships a CycloneDX SBOM of its Rust crates at `dist-info/sboms/cedarpy.cyclonedx.json`;
  all 131 crates there are permissive (MIT, Apache-2.0, Unlicense, Zlib, Unicode-3.0), with
  no copyleft among them. The release SBOM lists those crates inside cedarpy's component,
  read from that file in the image's own environment, and the release provenance's license
  disposition reads their licenses with the rest, so an undeclared or copyleft crate is named
  there as a Python distribution would be.
- `pyasn1-modules`: BSD-2-Clause. Its metadata says only `BSD`, with the `BSD License`
  classifier, which names a family rather than a license. The installed
  `pyasn1_modules-<version>.dist-info/licenses/LICENSE.txt` is the two-clause text, the same
  one `pyasn1` declares as `BSD-2-Clause` for itself.
- `jinja2`: BSD-3-Clause. Its metadata classifier says only `BSD License`, which names a
  family rather than a license, so the script does not read it as one. The wheel's
  `licenses/LICENSE.txt` is the three-clause text, non-endorsement clause included.
- `httpx2-jsfetch`: BSD-3-Clause. Declared as `License-Expression: BSD-3-Clause` in its own
  wheel, which is an Emscripten wheel this platform cannot install, so the metadata is not
  present to read. Read from the wheel for `wasm32-pyodide2025`.
- `pywin32`: PSF-2.0. A Windows wheel this platform cannot install. Its metadata says
  `License: PSF` with the `Python Software Foundation License` classifier, and `PSF` alone is
  not an SPDX identifier; `PSF-2.0` is, and is what the table records.
- `tzdata`: Apache-2.0. A Windows-only dependency of `psycopg` this platform does not
  install. Its wheel declares `License: Apache-2.0` and ships the Apache text.

## First-party distributions

- `execbound-client`: ExecBound's own package, installed from the working tree. The client is
  Apache-2.0: its `license` field and `clients/python/LICENSE` say so, and its installed metadata
  declares it. Its own
  dependency closure is a subset of the table above, and the one obligation in it is
  `certifi`'s: no LGPL reaches the client, because `psycopg` is the server's alone.
- `execbound-protocol` and `execbound-connectors`: ExecBound's own packages, installed from the
  working tree as runtime dependencies of the server. Both are Apache-2.0 and
  carry their license in `protocol/LICENSE` and `connectors/LICENSE`. The protocol depends on
  `pydantic` alone; the connectors on the protocol and `httpx`, and on `fastapi` through their
  `mock` extra. Every one of those is in the table above, and no LGPL reaches either package.

## Running the check

The same command the `verify` job runs, after any `uv add`, `uv lock` or `uv sync`:

```sh
uv run python scripts/python_sbom.py --lockfile uv.lock --dependencies DEPENDENCIES.md \
  --output local-data/release/sbom-python.cdx.json
```

It writes the SBOM whatever it finds, prints one line per problem and exits 1 if there was
one, so the SBOM is available to read even on a run that failed.
