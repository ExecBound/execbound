# Scout: effective authority and enforcement coverage

Scout answers one question about agents the customer already knows about: **what can each one actually do, through which path, and is that path governed.**

Status: the first source and Agents page are implemented. The [September 18 lab probe](#what-a-live-tenant-corrected-18-september-2026) read a small real directory and corrected collection and finding behavior. Inherited `allAllowed` permissions, attribution to a real agent and populated customer directories remain untested in that probe. The integration catalog retains a fixture-tested claim until a complete versioned trial record is available.

## What ExecBound does not do

**ExecBound does not find agents.** The customer's identity provider and platforms already list them, and endpoint, network and browser discovery belongs to the suite vendors — Agent 365 through Defender and Intune, Okta ISPM, SSE products. ExecBound consumes those inventories.

Three consequences the pages state rather than imply:

- **Agents with no identity are not counted.** Microsoft's own endpoint sweep classifies them; Graph does not serve them. ExecBound never asserts a number that would include them.
- **Azure RBAC assignments are not served by Graph at all.** An agent's reach into Azure resources is a hole, not a zero.
- **A group that carries a directory role is a reach path Scout does not follow yet.** A group membership is not a directory role, and the parser refuses to treat it as one.

Every tenant number states its denominator in words: *agents this connection could enumerate*, never *agents that exist*.

## The certainty ladder

A row's certainty is only ever what its own path can establish.

| Certainty | Established by | What it does not establish |
| --- | --- | --- |
| `verified` | An execution through ExecBound under a credential bound to this agent's linked principal | Anything about routes that do not traverse the kernel |
| `observed` | A Monitor observation of this agent executing the action, such as an entry in the directory's own audit log | That anything stood in the way |
| `inferred` | A grant, role or inherited permission the reviewed grant catalog maps to the action | That the agent has ever used it |
| `unknown` | A claim whose proof has lapsed | That the reach has gone |

A grant the catalog cannot explain produces **no reach row at all**. A row has to name an action, and naming one that cannot be established would be the invention the catalog exists to prevent. Those grants are counted and shown instead.

Freshness is read, not written: seven days for a grant snapshot, thirty for an execution or an observation, counted from its moment and never from later than the moment reach is derived, since no evidence is fresher than the pass reading it. Every agent's verified and observed reach is derived at each `process`, a page at a time, however many agents and actions sort before it. An expired row renders as `unknown` with the moment it lapsed, rather than being deleted, because deleting it would quietly shrink the denominator.

## Reach is per path

One row per `(action, path_kind, path_ref)`, never one per action. An agent that holds a directory grant *and* sends requests through ExecBound has two true answers to "through which path", and collapsing them is what would hide the alternate route.

A grant path can never claim an enforced mode. Nothing ExecBound operates stands between an agent and its own credential, so those rows are `unknown`. The [enforcement modes](INTEGRATIONS.md#enforcement-modes) are defined with the integrations.

**Adding a governed path does not close an ungoverned one.** Registering an operation mapping, a policy and an executor gives the agent a route that is enforced *for requests that traverse it*. The directory grant is still there. `ungoverned-reach.v1` therefore stays open until the grant is gone at a later collection, or until an ADMIN records an acceptance with `accept-reach` — which leaves the reach row exactly where it was, because deciding to live with a route is not the route disappearing.

## Accountability

Four states that a looser design would collapse into one, and only `absent` is a finding:

- `present` — sponsors (or, for a classic service principal, owners) are recorded.
- `absent` — the directory served the collection and it was empty. This raises `sponsorless-agent.v1`.
- `unreadable` — the directory refused the read. Insufficient evidence, counted separately.
- `not_read` — this run has not looked yet.

A sponsor is stored as an object identifier and a kind. No name, address or principal name is collected.

## The first source: Entra Agent ID

Read-only, through Microsoft Graph, under a **collection app registration separate from any registration that executes**. One client secret must never be both the executor and the collector. The collection registration holds `AgentIdentity.Read.All`, `Application.Read.All`, `AuditLog.Read.All` and `Directory.Read.All`, none of which can write. A registration that does not hold `AuditLog.Read.All` is still collected; its probe shows the `audit log` capability as `forbidden`, and the connection is not reported as complete until it is granted ([below](#what-the-directorys-own-audit-log-shows)).

A run makes exactly one `POST`, to the pinned login origin, for a token; every read is a `GET`. Graph returns the next page as a URL inside the response — the one place a request could be built from a response field — so a continuation is followed only when it is the pinned origin **and** the same path. A delta link is held to the same rule, and to more, because it is also stored ([below](#between-full-collections-delta-the-baseline-and-the-new-actor-rules)).

A run reads at most 1,000 principals. A directory that lists more, in its agent identities, its service principals or the two together, is refused whole with `AGENT_CAPACITY` and nothing from it is written; it is never read in part, because a principal past a silent cut would be marked gone, then stored for the first time by a later read and reported as new. A run reads each collection in at most twelve pages, enough for the bound when Graph fills the pages of 100 it asks for; a directory under the bound that Graph serves in shorter pages, so that the twelfth still offers more, is refused the same way rather than cut short. A delta pass is held to the same bound: one whose changes would leave the directory holding more is refused the same way.

The grant catalog and its gaps are documented in `src/execbound/monitoring/grant_catalog.py`: Graph permissions are keyed by published name and resolved to an identifier from the tenant's own `appRoles`, so no vendor identifier is copied into this project, and the directory-role identifiers that could not be established from a primary reference are named rather than recalled.

## Between full collections: delta, the baseline and the new-actor rules

A full collection reads the whole directory every six hours by default. Between full collections, each scheduled pass gives a directory a **delta pass** that reads only what changed, so a new principal is seen within minutes. The full collection stays the reconciliation.

**The delta link.** A full collection asks Graph for a `servicePrincipals/delta` link before it reads the directory, so a change made while it reads is reported again rather than missed, and keeps the link only if the collection completes. Only a collection that reads both the agent identities and the service principals asks for one; any other, like one that fails or gets no link it can trust, leaves the stored link where the delta passes left it. It asks for `$deltatoken=latest`, and where Graph refuses that, walks an initial round for its link and keeps nothing the round lists. The link is handled like any continuation: every next link and delta link must be the pinned Graph origin and exactly `/v1.0/servicePrincipals/delta`, a delta link must carry a delta token, and the connection keeps the link rebuilt from the pinned origin, the path and the validated query rather than as Graph sent it. A stored link is validated again before every use, and the database holds the same prefix as a check. The request a delta pass sends is always the pinned origin and path with that query; nothing in a response chooses where the next request goes. The pass asks Graph to track only the allowlisted fields `servicePrincipal` itself defines.

**What a delta pass does.** It runs when the directory holds a link and a baseline, its last full collection completed, it is not due for a full collection, no run holds it and no administrator's collection request waits. It takes the same lease as any run, through a claim of its own that the database refuses while a request waits and that never answers one, so a request made meanwhile survives it for the full collection to answer. It reads first: the round, then grants, roles and accountability for each principal the round lists. Graph may list a principal more than once in a round, a later entry carrying only what changed, so the pass lays a principal's entries one over the other: a property a later entry leaves out keeps what an earlier one said, such as the organization that owns its application, rather than reading as cleared. Only then does it write. It inserts a principal it has not seen, restores one marked gone, and marks a removed one gone with its grants and paths. Nothing else about a principal already held is rewritten, because Graph represents an updated principal with only some of its properties; its blueprint and name are refreshed by the next full collection. A principal's class is written once, from a record that states it, and is the store's after that, in a full collection as in a delta pass: a delta entry for a principal the store does not hold that carries neither the agent identity `@odata.type` nor a `servicePrincipalType` does not say whether it is an agent identity, so it is left for the next full collection, whose agent identity collection says so, rather than stored as a classic principal and read for owners instead of sponsors. It then runs the agent rules, and only then advances the link, so a pass that stops part way reads the same changes again. It never records an outcome, never moves the schedule and never changes the connection's health, even when the collector refuses its key file or platform app before any request, a refusal the next full collection records. That includes a pass that stops while it holds the lease: the lease is marked as a delta pass's, so the next claim takes it back without recording an interrupted run, and the next pass gives the directory another delta pass. A full collection that stops while it holds the lease is still recorded `INTERRUPTED` by whichever claim comes next, and a full collection, not a delta pass, follows it.

**When the link is dropped.** A 400 or 410 from Graph, as for an expired token, a stored link that no longer validates, a next link or delta link off the pinned read, a round past 20 pages or 1,000 changes, and changes that would leave the directory past 1,000 principals each drop the link (`RESYNC_REQUIRED`, `MALFORMED`, `DELTA_OVERFLOW`, `AGENT_CAPACITY`). Nothing from that round is written, the connection stays healthy, and the next full collection takes a new link. Any other refusal from Graph, while the pass reads the round or what its principals hold, keeps the link and writes nothing, and the next pass reads the same round again; that includes a page of the round that cannot be read, such as one that is not JSON or that carries both continuation links or neither (`MALFORMED`), because a page that does not parse says nothing about the link the pass started from. `collect-due` counts delta passes per workspace as `delta` and `delta_failed`.

**The baseline.** A connection's first complete full collection that read both its agent identities and its service principals is its baseline: everything is new then, so none of the three rules below speaks, and it opens one `initial-inventory.v1` summary on the connection instead, with counts only: actors enumerated, actors with consequential reach, actors with an ungoverned path, actors with nobody accountable and AI-publisher consents (without a sensitive-action list, the reach counts say they were not assessed). The `ungoverned-reach.v1` and `sponsorless-agent.v1` episodes that collection opens are recorded and listed like any finding, but are not delivered one by one, because the summary counts them. Connecting a directory therefore sends one message, not hundreds. A collection that could not read one of the two takes no baseline, no summary and no link, because a principal a later read stores for the first time was there all along and would be called new. What the connection's first run opens without reading both, as when Graph throttles the probe, is recorded and listed and waits, undelivered, for the summary the next collection is expected to send, and waits no longer: a later collection that cannot send the summary either delivers what waited, and what it opens is delivered one by one, as everything is when the registration is refused a collection outright and no summary can come until an administrator grants the permission. A connection that never reads both is therefore never silent about what it finds. When the summary comes, it counts what waited and still holds, and what waited and ended meanwhile is delivered with it: a finding that waited is counted or delivered, never neither. A connection that had already synchronized when migration `0093_scout_delta` was applied takes that upgrade as its baseline, whatever its latest collection's outcome, and raises nothing retroactively, unless it had never read the service principals, which list every principal in a directory: holding none of them, it takes its baseline, and sends its summary, at its first collection that reads both, as a connection that never synchronized does.

**The three rules.** "Consequential" is the detection profile's sensitive actions, as for `ungoverned-reach.v1`; without them `new-actor.v1` and `first-consequential-action.v1` are counted as insufficient evidence, while `new-ai-consent.v1`, which asks only whether an application comes from a catalogued AI publisher, needs no list. Each raises at most one finding per actor, ever. The finding names the actor, so the findings list shows it with its sponsor or owner count, and it queues a delivery like any finding. A delivery carries the finding's identifier and rule, not the actor, and nothing yet routes a finding to the actor's sponsors. Its episode closes when its condition ends and never reopens; a recurrence is `ungoverned-reach.v1`'s to report.

- **`new-actor.v1`**: an actor first seen after the baseline, within seven days of that sighting, holds a path to a consequential action that is not an ExecBound path and that no acceptance covers. The seven days catch a consent granted after the principal appeared without calling an actor new months after it arrived. The same path opens the actor's `ungoverned-reach.v1` episode, which is recorded beside it without a delivery of its own: one event, one message. It closes when the path goes, is accepted or the actor leaves.
- **`first-consequential-action.v1`**: an actor is observed, after the baseline and within the thirty days observations stay current, taking a consequential action with its own directory credential, outside ExecBound, whether or not it is linked and so holds a governed route for that action: a governed route stands in front of the requests that traverse it, not in front of the actor's own credential. The finding carries the earliest such observation; an actor already observed acting before the baseline never raises it. Its episode closes only when no such observation is current or the actor leaves the directory: a governed path appearing closes nothing. It is evaluated by `process`, after observed reach is derived, for every actor however many sort before it. A directory's evidence for it is its own audit log ([below](#what-the-directorys-own-audit-log-shows)), where an observation counts only when the action succeeded, so a refused attempt never raises it, and only when a read after the connection's first complete read found it, and a successful one that matches the execution ExecBound settled for it is left out, so ExecBound's own executions are not reported.
- **`new-ai-consent.v1`**: an actor whose application is in the reviewed AI publisher catalog (`src/execbound/monitoring/ai_publishers.py`) is first seen after the baseline, within seven days. It closes when the actor leaves the directory, which is how a removed consent appears. The catalog records each entry's primary source and the day it was read, matches an application by its `appId`, its owning organization or its verified publisher, and keeps only the entry's key. It holds Anthropic's two Microsoft 365 connector applications; OpenAI publishes no identifier for its applications and is named as a gap, and Microsoft's own applications are not entries.

`new-agent.v1`, which reported every principal first seen since the last run whatever it could do, is no longer raised; `new-actor.v1` reports a newcomer only when it can act. Findings it raised stay readable.

**Not yet established.** Whether agent identities appear in `servicePrincipals/delta`, the exact shape Graph gives a removed principal, and whether service principals honour `$deltatoken=latest` have not yet been confirmed against a real directory. The delta pass does not depend on the answers: an agent identity the delta does not list, or lists without saying what it is, is seen by the next full collection, and a refused `latest` is answered by an initial round.

## What the directory's own audit log shows

Every full collection and every delta pass reads the directory's audit log (`auditLogs/directoryAudits`, which `AuditLog.Read.All` grants) once its principals are written. An entry an application initiated that the reviewed **activity map** covers becomes one Monitor observation of the actor that took it. This is what turns reach into evidence of what an actor did.

**The read.** It asks for Core Directory entries from the connection's cursor, oldest first, in pages of 100 and at most four pages a run: the reports API allows five requests per ten seconds per app per tenant, and a full collection's probe is the fifth. A next link is followed only on the pinned Graph origin and the audit path, whatever case Graph spells the path in, and the request is always the pinned origin and path with the link's query, so nothing in a response chooses a destination. A page whose entries are out of time order is refused whole. A read has caught up with the log when it reaches the log's end, or when it reads an entry from thirty minutes or less before its own moment, where the next read starts anyway; so a directory busy around the clock, whose log never ends inside a run's four pages, still catches up as long as each run reads further than the time since the last one. A read stopped by its bound short of that is a backlog that the next run continues. A connection's first read looks back thirty days, which Graph answers with what its retention holds: seven days on Microsoft Entra ID Free, thirty on P1 and P2, and on Free only from the first time the reporting API is used. After that, the log is read at every full collection and every delta pass, so every five minutes or so where the directory gets delta passes and at its full collections where it does not, and its observations are kept, so retention bounds only the first look-back. At four pages a pass that is about 4,800 Core Directory entries an hour, or 400 an hour where only hourly full collections read the log; a directory that logs more falls behind, and what falls behind its retention is lost, which the health finding below says.

**The cursor.** The Connections page's *Audit cursor* is where the next read starts, to the second. After a read that caught up it is the read's moment less thirty minutes, so an entry Graph makes available a while after it happened is read by the next run and recognised if it was read already; after a backlog it is the second of the last entry read, never later than that moment, so that entry is read again and recognised. A read that never left the second it started in, as when a bulk change logs more entries inside one second than a run reads, leaves the cursor at its last entry to the microsecond instead, so the next read starts inside that second and reads on rather than reading the same entries again. It never moves back. An entry Graph makes available more than thirty minutes after it happened, once a read has passed it, is not read.

**What the read never changes.** A refusal while reading the log from Graph (throttled, unavailable, a page out of order, or a next link off the pinned read, whose page is kept) keeps what its earlier pages read and leaves the cursor at the second of the last entry it kept, but never later than thirty minutes before the read's moment, so an entry Graph makes available late is still read, or where it was if it kept none; a refusal from the connection's bound of 200,000 observations (`CAPACITY`, which keeps what fits) leaves the cursor where it was. Either is counted in `collect-due`'s `audit_failed`; a read stopped by its bound short of catching up is counted in `audit_backlog`. Neither changes the run's outcome, the connection's health state, its last refusal or when it is next due, because a run's subject is the directory's inventory. A registration refused the audit log is not asked: its probe records the capability `forbidden`, a delta pass does not read it either, and the page shows the gap.

**When the read falls behind.** The connection records the moment its reads stopped catching up, whether stopped by their bound or refused, and a read that catches up clears it. So does a run that does not read the log because its probe found the permission refused: a read Graph refused before the probe recorded the refusal does not leave an episode no read can end, and the first read once the permission is granted begins an episode of its own. Once that has lasted a day, `collection-health.v1` is raised once for the episode, *Collection has not caught up with the platform's audit backlog*, and delivered like any finding: until the read catches up, a connection that has not yet had a read catch up has no activity baseline and raises nothing from its audit log, and entries can age out of Graph's retention unread. A connection's first look-back raises it too where the directory is busy enough to take a day to read through. A read that starts from a cursor further back than thirty days, the longest retention Graph offers, raises *Audit retention passed the collection cursor; a window is unrecoverable* once for the episode, because what lay between the cursor and that retention is gone. Neither changes the connection's health state, which stays its inventory's. A connection that holds 200,000 observations reads no further, because nothing yet removes an observation, so every later read is refused too: the first read the bound refuses raises *Collection reached the connection's observation bound and records no more* at once, once for the episode, and a day of it raises the backlog finding as well. Until observations can be removed, the one way on is to revoke the connection and connect the directory again: the new connection has a bound of its own, and its own baselines, so its first read's look-back raises nothing, and it counts against the workspace's twenty connections, revoked ones included.

**The activity map** (`src/execbound/monitoring/activity_map.py`, version `entra-audit.v1`) is reviewed like the grant catalog: every entry names Microsoft's audit activity reference and the day it was read, and maps to an action the action catalog holds, which is checked when the module loads. An entry matches on the service that logged it, its activity name and, where one activity covers several changes, the one property it changed, and its one target must be a `User`:

| Activity (Core Directory) | Condition | Action |
| --- | --- | --- |
| Disable account | | `identity.disable` |
| Enable account | | `identity.enable` |
| Update user | `AccountEnabled` from true to false | `identity.disable` |
| Update user | `AccountEnabled` from false to true | `identity.enable` |
| Reset password | | `identity.reset_password` |
| Update StsRefreshTokenValidFrom Timestamp | | `identity.revoke_sessions` |

Role assignment is not mapped: the action catalog has no role action, and Scout claims no reach on an action outside it, as for Azure actions. Every other application activity, an entry whose values the map cannot read and one on any other kind of target are counted as unmapped and never stored, and one whose moment or id cannot be read is counted as dropped: whatever a field holds, an entry is counted and the read goes on. So is an entry stamped more than a day after the read's own moment, which has not happened by any clock the read trusts: nothing of it is kept, and since the cursor never passes the read's moment less thirty minutes, every later read meets it again and the first it is no more than a day ahead of keeps it, at the moment Graph stamped, where the clock-skew rule flags it like any entry more than five minutes ahead of its receipt. Every identifier is read whole, as the database's own checks read it, so one carrying anything more, even a final line break, is unreadable rather than stored. An entry a person initiated, or an application acting for a signed-in person, is ignored, and an application entry that names no service principal is counted as unattributed.

**What is kept.** One `entra_audit` observation per mapped entry: the actor's service principal object id, the target's object id, the action, the outcome (`success`, `error` for a refused attempt, `unknown` otherwise), the entry's id and its moment. No display name, principal name, address, reason, additional detail, application id or any other property value is kept. One actor's action on one target with one outcome under one correlation id, logged within ten seconds, is one observation, so a change the directory logs twice, as `Update user` and as `Disable account`, is recorded once, while a refused attempt and the retry that succeeded under the same correlation id, or two actors' entries under one, are recorded apart. A caller chooses its own correlation id and may use it again, so the same action on the same target under it logged later is an observation of its own, at its own moment: it is never folded into an earlier one, such as one that ExecBound's own execution accounted for, and it keeps the actor's observed reach current. Everything an observation asserts is in its identifier, so an entry Graph serves again under an id already read but asserting another result or another actor is another change, recorded beside the first, and no integrity finding can arise from it.

**What an observation raises.** A successful one derives `observed` reach for its actor and counts toward `first-consequential-action.v1`; a refused attempt is kept as evidence and derives nothing. An observation raises no finding of its own, so an automation that disables users every day sends no message a day, and an entry read long after it happened raises no clock-skew finding, because a log read on a schedule is behind its receipt by design; one ahead of its receipt still does. Each evaluation pass takes up to 400 audit-log observations, as many as one read stores, beside and never instead of its limit of the rest, so a back-filled log never holds back an action a source reports. Two further conditions apply to the rule:

- **The activity baseline.** A connection's first audit read that catches up with the log sets its activity baseline. What that read finds, with what the backlog reads before it found, is its actors' habit, however long after the directory's baseline it happened: none of it raises the rule, and an actor observed acting in it is part of the baseline. What a later read finds is news, even an entry stamped before the baseline read that Graph made available only after it, because the baseline is what was read, not a moment in the log; the connection dates it by when ExecBound received what it read, never earlier than anything the connection already holds, so a host clock set back after it does not turn a later read into the habit. An entry stamped at or before the directory's baseline is the habit, as for any evidence. An entry ExecBound's own execution accounts for, as the next condition reads it, is never the habit, however old: it is not its actor acting outside ExecBound, so ExecBound's own executor, whose executions the first read finds in its look-back, is still reported the first time its credential acts outside ExecBound. A connection whose reads have not yet caught up raises nothing from its audit log.
- **ExecBound's own executions.** An audit-log observation is left out only when exactly one execution in the same workspace matches it, one that settled `EXECUTED` through the Graph provider for the same action on the same target object id, the object ids compared without regard to case, with the observation within ten minutes of that execution's dispatch and settlement; and that execution matches no other observation. Two executions that match one observation, or one execution that matches two, leave out none of them, so an automation acting on the same target at the same moment is reported rather than hidden. An execution's observations are counted within the connection that holds them, because each connection holds one reading of its directory's log: a connection revoked and the one that connects its directory again hold copies of the same entries, which are one change, not two. An observation left out still derives observed reach, because it is true. The database cannot recognise ExecBound's own service principal, whose client id lives only in runtime configuration, so the match is the whole test. Home's board reads the same match: its band of what monitoring saw pass under the checkpoint draws a successful audit-log observation that the rule does not leave out, and neither one that ExecBound's own execution accounts for nor a refused attempt.

**Not yet established.** No real directory's audit log has been read: which activities an application's disable, reset and revocation log, how a modified property's values are written, whether `Update user` and `Disable account` share a correlation id and how far apart they are logged, whether the combined filter, the ordering and the case of Graph's next links behave as the documentation reads, and whether Graph takes and honours a moment to the microsecond in the filter, which only a read inside one busy second sends, are fixture-verified until a read-only probe of a real directory, with `AuditLog.Read.All` consented, settles them.

## Commands

```sh
uv run python -m execbound.monitoring.commands create-connection \
  --credential-file <admin> --label "<directory>" --kind entra_agent_id --key-file <private env>
uv run python -m execbound.monitoring.commands collect-entra \
  --credential-file <admin> --connection <id> --key-file <private env>
uv run python -m execbound.monitoring.commands link-agent \
  --credential-file <admin> --connection <id> --agent <object id> --principal <principal>
uv run python -m execbound.monitoring.commands accept-reach \
  --credential-file <admin> --connection <id> --agent <object id> \
  --action <action> --path-kind <kind> --path <path> --reason <CODE> [--days 90]
```

`link-agent` binds the agent to an active agent principal through the same functions as the Agents page's `Bind` (migration 0037), one to one, and reports `LINK_CONFLICT` for a second principal; `unlink-agent` withdraws the binding with the reason "withdrawn with unlink-agent".

The private file holds `ENTRA_DIRECTORY_ID`, `ENTRA_CLIENT_ID` and `ENTRA_CLIENT_SECRET`. The connection keeps only the secret's SHA-256 fingerprint; a key file whose fingerprint differs is refused before any request is made.

**On a schedule.** `collect-due --all-tenants --key-files <directory>` collects every due connection, in every active workspace, with no workspace credential, where the directory holds that connection's private file as `<connection id>.env`. An Entra connection is due six hours after its last run, or after its own interval of one to 24 hours, and at once when an administrator asks for a collection; between full collections, each pass gives it a delta pass, which never moves when it is next due. Every run, scheduled or `collect-entra`, holds the connection's lease for its duration, so two never collect one directory at once, and one whose connection is revoked mid-run writes nothing more. `process --all-tenants` derives observed and verified reach in every workspace the same way, without a credential. Both are described with their bounds in [Tines monitoring](TINES_MONITORING.md#scheduled-collection-and-evaluation).

**The collector.** Scheduled collection runs as its own process, the collector, which holds what opens a connection's credential and nothing else: operator key files, the private key that opens a Tines key pasted in the console and sealed for it ([Connect Tines from the console](TINES_MONITORING.md#connect-tines-from-the-console)), and the platform app's certificate below. The web service holds only the collector's public key and the platform app's public values, so it can seal a key and never read one back, and it can send an administrator to Microsoft but never read a directory itself; neither the collector's key nor the app's certificate is given to any other process.

## Connect Microsoft Entra from the console

Where the deployment names its own app registration for this (the runtime configuration's `scout.entra`, beside `scout.collector`), an administrator connects a directory by its administrator's consent rather than by an operator's private file. **Monitoring → Connect Microsoft Entra** says what the app reads, who can approve and how to withdraw, takes a connection name, and continues to Microsoft:

1. **Start.** ExecBound records an attempt in the Space you are looking at and sends your browser to Microsoft's sign-in, with a binding cookie in this browser (`HttpOnly`, `Secure`, `SameSite=None`) that only this browser holds. A full workspace, a Space that already has a Microsoft Entra connection, more than five attempts at once or twenty in a day are refused here, before you leave. The step asks for a recent second factor and refuses a personal access token.
2. **Sign in.** A Global Administrator or Privileged Role Administrator of the directory signs in. ExecBound verifies the id_token Microsoft posts back (RS256 against Microsoft's published keys, issued for that directory and for this app, current) and reads two claims only: the directory (`tid`) and the administrator's roles (`wids`). No name, address or object id is read, and no ExecBound person is looked up. A directory any workspace has already connected is refused here, before consent is asked for, with a sentence that names no workspace.
3. **Consent.** Microsoft shows the app's read-only permissions and the administrator approves. ExecBound creates one `platform_app` connection in the attempt's Space, asks for its first collection, and the page you return to says what happened from ExecBound's own record, never from the address.

Every refusal ends the attempt, creates nothing and logs only a code. An attempt lives ten minutes, its `state`, nonce and binding are kept only as digests, and a directory is connected once across the whole deployment, whichever way: `create-connection` for a directory another connection already reads answers `DIRECTORY_UNAVAILABLE`.

**What the app reads.** `AgentIdentity.Read.All`, `Application.Read.All`, `AuditLog.Read.All` and `Directory.Read.All`, all read-only, nothing that can write. The app is a separate registration from any that executes.

**The platform app's credential.** A certificate, in the collector's private file (`scout-app.json`: the app's client id, the certificate and its RSA key). The collector authenticates with a client assertion signed by that key (RFC 7523, RS256, naming the certificate by its SHA-256 thumbprint, five minutes, a fresh `jti` each time) and refuses a consented connection that names another app's client id (`CLIENT_MISMATCH`) before any request. Rotate the certificate every 90 days.

**The blast radius, stated plainly.** That one certificate reads every directory that consented to the app. It is read-only, it lives in the collector's environment alone, and each directory can remove the app at any time.

**Consent needs updating.** A consent can go stale: the first collection's probe establishes which permissions hold, and when a permission a connection had is refused later, its card says "Consent needs updating" and offers **Update consent**, which runs the same three steps for the same connection and the same directory only.

**Withdrawing consent.** Revoking the connection stops collection here and keeps what was collected. Only the directory can withdraw its consent: remove the app's enterprise application in Microsoft Entra, which the Revoke dialog names with its client id.

## Pages

`/monitor?view=agents` and `/monitor/agents/{agent_id}` are ADMIN-only console views inside the monitoring authority predicate; the former `/monitor/agents` list address redirects to the query view. The list carries the tenant line and its denominator; the detail page shows every path with its certainty, mode and freshness, every grant with what it reaches, the findings and the observations attributed by object identifier. Its **Govern this agent** opens `/agents/{agent_id}` with the same identifier, where the agent can be governed (a principal, a binding and a first API key in one step) or bound to an agent principal that already exists; a linked agent offers **Open the governed agent** instead. The `link-agent` and `accept-reach` commands sit folded under **Operator commands** where the deployment's console offers them. On the Agents list, a row with consequential reach and no link offers **Govern**, and a linked row links to its governing agent. The way back is the agent page's own note, which links to this agent's Monitoring page.

### The Agents page

`/agents` puts the agents a connection lists beside the agent principals ExecBound governs ([SURFACES](SURFACES.md)). What it claims, and what it does not:

- **A binding says that one agent principal *is* one listed agent.** An administrator makes that statement with `Bind`, `Govern this agent` or `link-agent`; nothing infers it, and a display name that resembles a principal is not evidence. It is one to one while active and is withdrawn with a reason, never deleted.
- **A binding governs one route, not the agent.** The bound principal's executions through ExecBound become that agent's verified reach; every grant, role and inherited path the source reports stays exactly what it was, ungoverned until something stands in front of it. Being bound is never a claim that the agent can do nothing else.
- **`Govern this agent` creates a principal, a binding and a credential in one step.** Until the agent's host uses that credential, nothing it does passes through ExecBound; the page says so beside the secret.
- **The tenant line counts what a connection could enumerate**, per source, with Monitoring's own definitions of consequential reach and of reach not established, so the two pages cannot disagree; it never counts agents with no identity, and a source that lists none has not shown that it holds none.

## What a live tenant corrected, 18 September 2026

A read-only probe, and then a full collection, ran against a test tenant created that day (Entra ID Free, no premium licence). It answered the open questions and found two defects in shipped code and one overstated assumption. The tenant holds one agent identity, one blueprint, one sponsor and twenty-six of Microsoft's own first-party service principals.

**Agent ID is served on the free tier.** All five capabilities classify `available`: agent identities, service principals, applications, grants and directory roles. Both Agent ID cast collections answer `200` in a tenant with no P1, P2 or Agent 365. The `Agent ID Administrator` and `Agent ID Developer` role templates exist. This was the largest unknown and the answer is the permissive one.

**Defect: the cast collection carries no `@odata.type`.** `GET /servicePrincipals/microsoft.graph.agentIdentity` returns agent identities with the field absent entirely, and `parse_agent` classified on exactly that. Every agent identity in a real directory would have been filed as a classic service principal with its blueprint reference dropped — Scout would have reported zero agents while showing them under the wrong class. The parser now takes three signals in order: the cast collection is the type assertion, because the URL says so; `@odata.type` where an endpoint sends it; and `servicePrincipalType`, documented as "set to `ServiceIdentity` for all agent identities". A tag is still only evidence and still never decides a class.

**Defect: `/directoryRoles` refuses a page size.** It answers `400 Request_UnsupportedQuery` — "This resource does not support custom page sizes" — and the capability probe sent `$top=1` to every path. The capability classified `unknown`, and because the detail pass only reads roles for an `available` capability, **every directory-role grant was skipped in silence**. Page size is now a property of the resource rather than of the reader.

**The expected blocklist holds, and there is a second constraint.** `User.EnableDisableAccount.All` and `User.ReadWrite.All` are refused for an agent identity: *"The specified app role cannot be granted to agent identities."* So is a directory role — *"the specified role is not allowed for assignment to agentic entities"* — which no reference consulted beforehand mentioned. `User.Read.All` and `Directory.Read.All` are granted normally.

The consequence is a real narrowing of what Scout can find in Entra, and it belongs on the page rather than in a footnote: **an agent identity cannot hold a direct grant to any consequential identity action.** Ungoverned consequential reach in an Entra directory therefore comes from classic service principals, which carry no such restriction, from inherited blueprint permissions, and from Azure RBAC, which Graph does not serve at all. An agent identity's own grants are a much shorter story than first assumed.

**Two smaller facts.** A blueprint's object id and its `appId` were identical, unlike an ordinary application, which makes resolving `agentIdentityBlueprintId` cheaper than feared — one sample, not a rule. And the sponsor requirement is enforced at creation: a blueprint without one is refused with "No sponsor specified."

**A product question the probe raised, and the answer it got.** Twenty-six of the twenty-seven principals enumerated are Microsoft's own first-party service principals, none of them owned, so the first run opened twenty-six `sponsorless-agent.v1` episodes — literally true and useless. The directory answers it with a fact rather than a heuristic: `appOwnerOrganizationId` names the organization whose application a principal represents, and twenty-four of the twenty-six name Microsoft's. The rule now carries two conditions:

- **A principal another organization owns is not the customer's to sponsor.** Nobody can assign accountability for the Workload Identity Control Plane, and asking is how people are taught to ignore findings. Null means the application was registered in this directory, which is how a locally created agent identity appears, so null counts as theirs.
- **A principal that reaches nothing consequential is not worth reporting.** Without it the rule degenerates into "this tenant contains service principals", which is always true. With it, every sponsorless finding names something that can act.

Neither condition hides anything: all twenty-seven principals stay in the inventory and in reach computation, because a consented third-party application holding write access to users is a real risk — it is simply not a question about sponsorship. Re-run against the same tenant, the rule raises **zero** findings and every episode closes, which is the right answer: nothing there is both unowned and dangerous.

**What stays fixture-verified.** Inherited `allAllowed` blueprint permissions were not exercised, no observation or execution was attributed to a real agent, and no tenant with a populated directory has been read. Those pages still say so.
