# HTTP, MCP and human review

The private runtime exposes two endpoint actions and four identity actions through two adapters. Both call `Runtime.execute`, which validates strict input, commits authority through the execution coordinator and consumes a newly issued dispatch ticket internally. Tickets and provider credentials never appear in responses. Connector availability is checked against both the resolved account and provider kind before a new execution can reserve capacity.

## Agent interfaces

- `POST /v1/execute`: original JSON body is an `ActionRequest`.
- `GET /v1/executions/{execution_id}`: current AGENT credential, own tenant and principal only.
- `GET /v1/actions`: current AGENT credential; the operations the agent's own space offers, with each one's arguments and target kinds, and never a target, a rule, a limit or a placement ([threat model](THREAT_MODEL.md#b1-protected-agent-to-gateway), T1.17). No body and no query string.
- `POST /v1/executions/{execution_id}/outcome`: an external executor's report on the grant it holds for that execution. The same authentication as every other agent route; the report secret in the body names which grant is being settled and is no substitute for the credential. The act grant is not presented here and cannot be — extra fields are refused — because the report window deliberately outlives the act window. See [External execution checkpoint](CHECKPOINT.md).
- `POST /pre` and `POST /post`: a control point's Pre- and Post-Execution hooks, served only when the private configuration carries an `arcade` block and normally reached through the separate `create_arcade` process. The same AGENT authentication and the same request discipline as the routes above, and a different **body** rule: the monitoring intake's, which admits `application/json` and `application/json; charset=utf-8` compared case-insensitively and nothing else, each route under its own byte bound. See [Arcade logic extension](ARCADE.md).
- `/mcp/`: authenticated stateless Streamable HTTP, with `execute({"request": ...})`, `execution_status({"execution_id": ...})` and `list_actions()` tools. A `tools/call` may leave `arguments` out; when it is sent it must be an object. Use the trailing slash.

All agent requests carry `Authorization: Bearer <credential>`, where the credential is the agent's API key, an opaque token an administrator issues in the console or with the CLI ([Get an API key](https://docs.execbound.ai/api/agent#description/authentication)). It does not implement OAuth discovery, an authorization server or external identity federation. MCP client metadata, tool caches, session identifiers and logical runs cannot establish authority. Every MCP tool call is logged as `mcp.call` with the tool name, the protocol revision the request carried and the client's self-reported name and version (cut to 80 characters), identifiers that establish nothing; never the arguments, never the result. The `execute` tool accepts `reference` in place of `idempotency_key` and derives the key exactly as the Python client does, so a model-driven host is never asked to invent a key.

The service pins official `mcp==2.3.0`. Compatibility tests run the current client (protocol `2026-07-28`) and the actual maintained `mcp==1.30.0` client (protocol `2025-11-25`) in an isolated, hash-locked environment. This is SDK compatibility evidence, not validation with a named practitioner's host application. The [official releases](https://github.com/modelcontextprotocol/python-sdk/releases) identify the two supported release lines; the [ASGI integration guide](https://py.sdk.modelcontextprotocol.io/run/asgi/) describes the transport lifespan.

Raw MCP JSON passes duplicate-key, numeric, envelope and size checks before SDK decoding. The tool argument schema is generated as a complete wrapper so references resolve in validating clients. Unsupported protocol input responses, request state and task fields cannot become human approval. Action arguments go through the same parser as HTTP, which admits only bounded scalars, and then through the same catalog normalization during resolution, which rejects anything outside the resolved action's spec before a fact is read.

Pending results contain execution/approval IDs, the frozen plan hash and a signed status continuation when runtime keys are configured. The continuation binds tenant, principal, credential, audience, IDs, plan, expiry, nonce, key ID and HMAC-SHA256/version. `execution_status` accepts an optional `continuation`; HTTP status accepts `X-Execution-Continuation`. A continuation only validates status metadata. It never grants approval or replaces current authentication. Unknown/retired keys, altered scope, expiry and noncanonical encodings fail closed.

There are four audiences. The fourth, `execution.checkpoint_outcome`, is the act grant beside a checkpoint; it is the only audience that carries an `operation_id`, which the other three refuse outright so the field cannot be attached to a status, approval or reconcile token to make one look like authority over an operation. The field serializes only when set, so a continuation of the other three audiences is byte-identical to one issued before the field existed. Nothing in ExecBound verifies the checkpoint audience today: it is a signed statement the executor holds, and the outcome route authenticates on the report secret instead.

HTTP uses 202 for pending or uncertain execution, 200 for terminal state, and bounded errors for invalid input (400), invalid role (403), scoped absence (404), conflicts (409), load limits (429) and unavailable dependencies (503). A terminal `DENIED` is an execution result, not a successful mutation. MCP returns the same state data in structured tool results, with `isError` for request failures.

## Human interfaces

### Accounts and workspace selection

**Workspace switching is core**: `GET /api/console/v1/session/workspaces` and `POST /api/console/v1/session/workspace` below answer on every deployment, with or without a plugin, and the session's `can_switch_workspaces` is true for any session signed in through an account.

Personal password or an already-bound provider subject signs in to an account. Its workspace
memberships supply local permissions; losing access to the original workspace leaves another
active membership usable. Unverified legacy addresses retain their original workspace access
but cannot gain expanded membership merely from their stored address. Unknown provider subjects
are not attached by matching email. A signed-in owner starts explicit linking with
`POST /account/link/{provider}` from account security, using CSRF, recent authentication,
verified email and required MFA; the callback consumes one state/provider/session-bound proof.
An account with no password, as a Google, GitHub or Microsoft signup leaves it, is offered a first one on
account security: `POST /account/security/password` takes `csrf`, `password` and `confirm`,
compares the two as bytes, and calls `set_first_password` under the same bar as linking. It
never replaces a password, which `/settings` changes with the current one; every refusal is a
sentence on the page, and the change ends the account's other sessions.
The organization's MFA requirement (everyone, administrators, or each person's choice) is set
on the same page by a workspace administrator alone (decided 8 October 2026, migration
`0074_workspace_settings_admin`), because it applies to every person of the workspace: an
administrator narrowed to spaces is not offered the form, `POST /account/security/policy`
answers anybody who is not a workspace administrator 403 before anything is written, and
`account_security_change` and `user_security_change` refuse it `RECENT_AUTH_REQUIRED`, the
answer an approver gets.
Legacy administrator password codes remain bootstrap-only for unlinked principals.

`GET /api/console/v1/session/workspaces` lists the current account's usable memberships. Each
item names the workspace, the kind a session there would carry, the roles it grants across the
whole workspace (a role granted in one space is not one of them) and what entering it asks
beyond this sign-in: `open`, `factor` (the switch asks for the account's code), `enrol` (it asks
for a factor to be set up) or `directory` (only the organization's own sign-in opens it). Where
the switch would carry this session's verification (below), a workspace that asks for a code is
`open`: the current session's own verification is read once, under its own workspace's row
security, before any other workspace is entered. For a
workspace other than the current one whose entry is `open`, the item also carries how many
approvals wait there for this account's principal, read with the pending approval queue's own
predicate under that workspace's row security, capped at 100, and the earliest of their deadlines
floored to the minute (`waiting_state` `counted`). A count is a number, never a record, and it is
withheld, with no count read, wherever entering asks for more proof (`withheld`); past the 25th
workspace nothing more is counted (`not_counted`). Each item also carries `last_entered_at`, when
this account last entered that workspace (null for one it never has), from the account's own
membership record; the menu orders by it after the current workspace. The list is read again with
the session, never on a timer of its own and never in a hidden tab, and reading it writes no event.
`POST /api/console/v1/session/workspace` requires the account cookie, CSRF and the displayed
`X-ExecBound-Workspace` session generation. Selection recomputes roles and MFA requirements,
invalidates the old workspace session and resets the Space view. The new session carries the old
one's second-factor verification when, inside the switch, that verification is of the account's
current, enabled factor and is under thirty minutes old, the step-up window; the carried
verification keeps its own time, so the thirty minutes still count from the code, and nothing
else of the old workspace is carried. A carry is recorded twice: for the account, with the
workspace and session it came from and the ones it opened, readable only by the account itself;
and as `account_security.assurance_carried` in the workspace it opened, which names no other
workspace. Older verification, a factor since replaced or removed, and a workspace that asks for
a factor of an account with none still ask, as before. Required-directory entry
fails closed and directs the person to ordinary organization sign-in. Setup credentials and
customer OIDC alone cannot acquire account switching or global account-management authority.
The body may name the `section` the person is on, one of a closed set of console page roots
(Home, Approvals, Activity, the Live board, Policies, Agent connections, Users, Groups & roles,
API keys, Approval rules, Spaces, Monitoring, Getting started, Workspace settings, Help and My
account), never a record, a query or another address; anything else is 400 `INVALID_BODY`. The
answer is that section when the new session may open it, else where that session starts
(Approvals for an approver who may decide, Home for everyone else), or `/mfa` when the
destination asks for a factor, in which case the signed five-minute return cookie carries the
section through the code. The switch writes nothing but a section into that cookie; a section root
is also one of the console pages a sign-in link may name (`GET /login?review=`, below).

The workspace selector is separate from the Space selector. A switch clears cached data and
live streams. Every other tab of the browser replaces its page with one that names the workspace
it showed and where the browser is now, and links to its section's root in the new workspace,
never to a record; after a sign-in again to the same workspace it offers to reload its own page
instead. Tabs tell one another over a broadcast channel; a message is shape-checked, shown as
text and grants nothing, and a tab acts on another tab's sign-in only once a read of
`GET /api/console/v1/session` answers with that session's generation in its header. Requests and
stream reconnects carry their original generation so stale controls cannot act in the newly
selected workspace. Personal
session cookies last up to the credential's absolute expiry, while the server enforces the
fifteen-minute idle limit on every request. Ordinary reads renew server state without rewriting
those cookies, preventing a delayed old-workspace response from overwriting a new selection.

Approval notifications link to `/approvals/{approval}` (and its own classic suffix), or to the
workspace-scoped address a loaded plugin registered for approval links. Signing in from a
workspace-scoped approval address opens that workspace when the account is an eligible member of
it; once signed in, a different workspace still requires explicit selection. Without such an
address, a sign-in opens the eligible workspace the account entered most recently (by signing in
there or switching to it), else its oldest membership. Opening a notification never switches the
workspace of a session that already exists or grants review permission by itself. After a
switch that asks for a code, the second step names the workspace it opens ("Verify to open
{workspace}"); a code that
was just used, the one still on screen after it opened another session, is answered as such and
never counts toward the five-attempt lock. Account
security history and global sign-out belong to the account owner. Local administrators manage
local membership/session access and cannot reset the shared password/MFA or turn a local
privacy-request resolution into global account deletion. Teammate invitation
acceptance is its own flow, below; these account primitives do not enable it.

### Existing sign-in and review routes

**The console is a single-page application served at the console's own paths**. `GET /`, `/activity`, `/agents`, `/agents/{agent_id}`, `/approvals`, `/approvals/{approval_id}`, `/approvers`, `/access`, `/ask`, `/ask/{turn_id}`, `/board`, `/credentials`, `/monitor`, `/monitor/agents/{agent_id}`, `/people`, `/people/{person_id}`, `/policy`, `/policy/{bundle_id}`, `/policy/{bundle_id}/rules`, `/report`, `/settings`, `/help`, `/spaces`, `/tenant` and `/welcome` each serve the application's one document to a signed-in person. Those are exactly the addresses core's application has (`CONSOLE_ROUTES`): the server enumerates them rather than answering from a catch-all, `tests/test_console_serving.py` holds the list equal to core's generated route tree, and an address outside it answers 404 rather than a shell that would render "not found" with a 200. A plugin's console edition adds addresses of its own, which the server answers only where that plugin is loaded ([How the console is served](#how-the-console-is-served), **Editions**); the hosted service's are documented with the hosted service.

**A person signs in through their existing account**, with an email and password, a configured provider or their organisation's directory. `GET /login` offers the password form posting to `POST /session/password` and configured provider buttons, and links "Forgot your password or lost access?" to the deployment's help page where its `service` block names one ([below](#private-configuration-and-startup)). It has no review credential field. Below every way to sign in it may carry one plain link a loaded plugin registered, on the page itself and on every refusal that lands back on it; core adds none. A loaded plugin may also register a recovery link (`Registry.recovery_link`, held to the same rules): with one, the page shows it in place of "Forgot your password or lost access?" and keeps the deployment's help page for a lost second factor, as "Lost your authenticator app and recovery codes? Get account help". The hosted service's reset by email is documented with the hosted service. The explicit installation entry point `/login?setup=1` retains the setup credential exchange at `POST /session`; it grants no review permission. [Reviewing actions](REVIEWING.md) describes assignments and notification links. A provider's flow is `POST /login/{provider}` and `GET /login/{provider}/callback`; a name no block configured answers 404, so nothing a request sends chooses a flow. Where a loaded plugin registers `Registry.provider_signup`, a page that started the same flow for a signup — never `/login` itself — sets a `provider_signup` intent cookie beside the ordinary one, and the callback reads it once and dispatches to that point instead of the ordinary sign-in once the flow completes: a mismatched or unregistered intent is refused rather than quietly falling through to a sign-in, and a flow with no such cookie reaches the ordinary sign-in exactly as before. A successful callback answers with a page of this application's own, "Signed in." with a refresh and a link to the landing page, rather than a 303: the provider's redirect back is a cross-site navigation, a request that follows a redirect in that chain is sent without the SameSite=Strict session cookie the callback just set, so a 303 would land a signed-in person back on `/login`. The session cookie stays Strict; what changes is that the next request starts on this site. `GET /set-password` and `POST /set-password` redeem a one-time code an administrator or owner tooling minted.

**Signing in returns a person to their place.** `GET /login?review=<address>` keeps the address as a navigation hint: a signed, HttpOnly, Lax, five-minute cookie under its own HMAC domain, refused when duplicated and deleted once a session is issued without a pending factor. What it may name is one closed grammar, `login_return.canonical`, which every writer and reader of the hint uses: one of core's own console route shapes with lowercase-UUID parameters (the workspace-scoped approval address only where a loaded plugin's approval links mount it; a plugin's own console pages are never returnable), with no second origin, backslash, fragment, encoded slash, whitespace or control character, at most 512 characters in and 256 out. On five pages a few query keys are kept, each with a UUID or a value from a closed list (Home's `open` and `range`; Activity's `open`, `agent`, `target`, `state`, `since`, `action` and `outcome`; Approvals' `view`; Monitoring's `view`, `state`, `open` and `focus`; Getting started's `step`), sorted; every other key is dropped, and a key given twice refuses the whole address. None of the kept keys acts on load: each only chooses what the page shows, and a key is admitted only after its page is checked to act on a click alone. An address the grammar cannot use (a stale tab, a route this server does not have, a hand-typed address) still reaches the ordinary sign-in page, sets no hint and **deletes** any hint the browser already holds, so a garbled link lands on the landing page. A console page opened without a session answers 303 to `/login?review=` with its path and query, or, when only the second factor is pending, signs the same hint before it answers `/mfa`. The hint grants nothing: every page it returns to re-authorises its reads. Every one of them is public, carries its own CSRF cookie compared with the field, applies the exact `Origin` check on the post, and counts against the peer limit and the per-address `login` limit; a wrong address and a wrong password answer 401 with the same sentence, and the private reason reaches `record_failure` and the structured log alone.

**A workspace administrator registers one OpenID Connect provider of the tenant's own**, on tenant settings, and it is a row rather than a block in the configuration file: the issuer, the client id, the subject claim (`sub`, or `oid` for Entra ID) and a client secret kept as AES-256-GCM ciphertext under the deployment's `sign_in.directory` key ring. Without that ring there is nowhere to keep a secret, so no provider can be registered, the card says so and every route below answers 404. Discovery is fetched and validated at registration and the three endpoints are stored on the row, so a document that changes later cannot move a live flow; an Entra issuer must name one directory, and `common`, `organizations` and `consumers` are refused. The deployment's own Microsoft button, which a `sign_in.microsoft` block configures, is not this: it is a personal sign-in method like Google, uses the multi-tenant `organizations` authority, signs in only an account that linked it, and never opens a workspace that requires sign-in through its own directory. A provider is `draft` until the administrator completes a real sign-in through it, which links their own account and marks it `verified`; `enabled` makes it available and `disabled` revokes every directory session under it. **Only a workspace administrator configures it** (decided 8 October 2026, migration `0073_directory_workspace_admin`), because it signs people in to the whole tenant rather than to a space: an administrator narrowed to spaces (no workspace-wide `access.manage`, and a membership of any space) still reads `GET /api/console/v1/tenant/sign-in`, which their people's invitations stand on, and the card shows them the provider with a note in place of `Register a provider`, `Test sign-in`, `Enable` and `Disable`; `POST /api/console/v1/tenant/sign-in` and `POST .../{provider_id}/state` answer them 403 before discovery is fetched or anything is written, as the access page does, and `directory_register` and `directory_set_state` refuse them `INVALID_ACTOR` again. One redirect URI serves every tenant: `<origin>/login/directory/callback`. The flow is `POST /login/directory/{provider_id}` and that callback, with `GET /login/directory/{provider_id}/link` for a signed-in person binding their own account. A workspace administrator may start that self-link through a draft, which is the test sign-in that verifies it; anybody else, an approver or an administrator narrowed to spaces, only through an enabled provider, from My account, and a draft or verified provider answers them 404 as the public start does. `directory_store.link_self` refuses the same again before `directory_link_self` runs, and since 0073 the function refuses it itself (`INVALID_PROVIDER`); before then it accepted an approver's sign-in through a draft as the evidence that verifies it. The callback ends on the same page of this application's own as a provider's, "Signed in." or, for a self-link, "Linked.", and for the same reason. The transient `__Host-eb_dirflow` cookie is the one SameSite=Lax cookie these routes set and carries a MAC under the same ring, because the callback is a cross-site redirect back and the session cookie is not sent with it: which invitation is being redeemed and who is linking come from that cookie, so it has to be one only this server could have written. `GET /invite` and `POST /invite` redeem a one-time invitation code, `ebv1.<tenant_id>.<invitation_id>.<secret>`, stored only as its SHA-256, single use, one hour to fourteen days, revoked by five wrong secrets and by the next code, and never in a URL; the sign-in that follows binds the subject to the invited person in the same function call that consumes it. `/login` offers the tenant's button to a browser carrying `__Host-eb_directory`, a hint cookie a successful sign-in through that provider set, so the form never says which addresses exist or where they work.

**A directory session is rechecked against its provider before it is renewed.** A session renews once half of its fifteen minutes has passed, and at that point the refresh token is redeemed at the stored token endpoint, outside every database transaction, whenever the last verification is more than five minutes old. `invalid_grant`, or an ID token whose subject or `tid` changed, revokes the credential and every session under it on that request, which is what Entra ID and Okta both answer once an account is disabled, deleted or has its sessions revoked. Every other error word, `invalid_client` included, is unavailability: the session stands while the last verification is within fifteen minutes and is refused after that, and nothing is revoked, so a directory outage that resolves lets people carry on rather than forcing a tenant-wide sign-in. A password or credential session reads one indexed row and reaches no directory at all.

Whatever proves who the person is, **a verified sign-in mints an internal credential row whose secret is discarded and `issue_session` runs unchanged**, so sessions, CSRF, cookies, renewal, revocation and the recheck are the same for all three and the role comes from the person's `principals` row either way. The OAuth flow cookie is not SameSite=Strict: `__Host-eb_signin`, HttpOnly, five minutes, carrying the `state`, the nonce and the PKCE verifier, is **Lax**, because the provider's redirect back is a cross-site top-level navigation and a Strict cookie would not be sent with it. It is deleted on first use, so a replayed callback has nothing to match. The pages' `form-action` names the authorization host of each configured provider, because that directive governs the redirect a form submission follows; each host is pinned in that provider's module and is in the policy only because a block named the provider.

A set-password code is `ebp1.<tenant_id>.<reset_id>.<secret>`, stored only as its SHA-256, single use, expiring between an hour and fourteen days, revoked by five wrong secrets and by the minting of the next one. **It never appears in a URL**: what an administrator hands over is the address to open and the code to type, as a directory invitation code is. Redeeming one revokes every session and credential the person held, because a code somebody could have read is a recovery and a recovery must not leave the previous holder signed in.

**Three things stay server-rendered**, because they run before a session exists or because a script cannot be relied on: `/login` (with the password form, a provider's two routes and `/set-password` beside it), the HTML error pages, and `/approvals/{approval_id}/classic`, the classic approval page every approval notification links from its footer and the console's own approval route links from its error boundary. They take a small stylesheet of their own, `/assets/app.css`, on the console's tokens and IBM Plex, and none of them loads a script.

**The addresses that moved redirect permanently**, so a bookmark, a browser's history and a link in an old message all still arrive: `/admin/people` to `/people`, `/admin/people/{id}` to `/people/{id}`, `/admin/credentials` to `/credentials`, `/admin/approvers` to `/approvers`, `/admin/settings` to `/tenant`, `/policy/rules` to `/policy`, `/monitor/{view}` to `/monitor?view={view}`, and `/next` and `/{route}`, where the console was served while it was being built, to the route itself. Each target is a constant path with only its path parameters substituted and the original query string carried; nothing in the request selects a host or a scheme, and a redirect reads no session and touches no row.

Open `/login` and use normal account sign-in. An approval notification returns a signed-out person to the exact request after sign-in, using a signed five-minute navigation cookie (Lax, HttpOnly, cleared after sign-in). It grants no authority and accepts no arbitrary return URL. Sign-in issues an opaque session and CSRF cookie; only hashes are retained in PostgreSQL. Sessions expire after 15 idle minutes and never outlive the original credential; a page load made after half the lifetime renews the session for another 15 minutes, never past eight hours from sign-in, and the response re-issues the cookies with the new age, so a reviewer who keeps reading stays signed in. The approval page names which clock set the expiry, the tenant's approval deadline or the plan's context validity, and its decision form stays valid for the session and the approval rather than for two minutes. Five active sessions per credential are permitted. Logout revokes the retained session immediately. Credential expiry changes, revocation, role changes and disabled principals/tenants invalidate existing sessions.

Both human account kinds see Approvals within explicitly assigned space/canonical-target/action scope; HUMAN_APPROVER also has scoped Activity access. A permitted person opens one approval's detail (`/approvals/{approval_id}` in the console, and `/approvals/{approval_id}/classic` the server-rendered page behind it, the classic address the console's notifications and error boundary fall back to for a phone whose console does not load or that blocks scripts) to review the frozen facts with their source, writers and observation time, the obligations, the applicable limits (each labelled with its scope, `Group <name>`, `Account <id>`, `<fact> = <value>`, `Principal` or `Tenant`, and its action list, rendered as inert text; the Activity review details show the same list), the decisions so far and the time left, then approve or deny with an optional bounded comment that lands in the audit event. Every page has one `h1`, labelled controls, captioned tables with scoped headers, a skip link as the first focusable element and a one-column layout at phone width; `tests/test_browser_console.py` runs axe-core over every console route in both schemes at 1280 and 390 px, and `tests/test_browser_accessibility.py` audits the pages that stay server-rendered. A browser request (one that accepts `text/html`) that fails answers an HTML error page with the same status as the JSON error and only generic, status-keyed copy (session ended, wrong role, not found, already decided or changed, emergency stop, too many attempts, unavailable) with links to sign in and home; API and intake clients keep the JSON body. An ADMIN manages policy bundles from `/policy` (list, create a draft from JSON) and `/policy/{bundle_id}` (inspect, validate, preview, activate with confirmation, retire) through the same audited store functions as the CLI. An ADMIN also issues and revokes agent and approver credentials from `/credentials` (a new secret is rendered exactly once, on the issuing response, and never stored or shown again) and manages approver assignments from `/approvers`; both pages write only through the `SECURITY DEFINER` database functions of migration `0021_admin_functions`, which recheck the tenant and acting ADMIN inside the database. Credential administration still refuses ADMIN principals and credentials, while migration `0045_review_permissions` permits review assignments on existing ADMIN accounts, so the gateway holds no table write privilege and cannot create or change administrators. An ADMIN also reviews read-only platform collection: the Connections page shows the collection connection's pinned origin, team scope, probed capabilities with their classification and probe time, health, audit cursor and last run beside the reporting sources, and Monitoring's inventory view lists discovered stories with the coverage class the reconciliation assigned and credential metadata, stating that action options, credential values and addresses are never retained and that an ordinary action's effect is not an audit record. Collected rows on the Activity page carry the `collected` evidence label with their operation name and actor reference. Monitoring's agents view and `/monitor/agents/{agent_id}` show what each agent a directory lists can reach, through which path, and whether anything governs it: the list carries a tenant line that states its denominator in words and names the two things Graph does not serve, and the detail page shows every path with the certainty that path can establish, the enforcement mode it can support and the moment its proof lapses, beside the grants, findings and observations attributed by object identifier ([Scout](SCOUT.md)). The activity list is the operations console: filters by state (including the uncertain queue of committed and indeterminate operations), action, agent and time window, cursor pagination of 50 records, dispatch evidence on uncertain rows and the ADMIN reconciliation form; query strings are refused everywhere except the keys that list accepts. Both roles have a tenant home at `/` (an approver's pending approvals first; for an ADMIN the figures, the decisions chart, what needs them and the recent decisions) whose rows open the record drawer and which changes nothing. ADMIN sees tenant Activity and can request evidence-based reconciliation with a reason. AGENT cannot sign in or use these methods. Approvers cannot reconcile; administrators cannot substitute for assigned human approval.

The hosted service adds its own signup and onboarding pages (`/signup*`, `/onboard`); they are documented with the hosted service.

Three routes and one asset serve teammate invitation acceptance: **`GET /join` is static and side-effect free**, `GET /assets/invite.js` moves the link's fragment (`#ebt1.<tenant>.<invitation>.<secret>`) into the form and out of the address bar and history before anything else can read it, and a browser with scripts blocked is shown a paste box instead. **The page is `/join`, not `/invite`**: `directory_pages.py` already serves `GET/POST /invite` for the customer-directory one-time invitation code, mounted ahead of this feature's own router, and Starlette hands a request to the first route that matches path and method, so a second `/invite` route here would never be reached. **`POST /join`** is the exchange: it reads only what the link is for through `inspect_invitation`, changing nothing but a wrong guess's failure count, answering `retry` (503) rather than `invalid` for a fault on the server's side (`INVITATION_UNAVAILABLE`), the same recoverable page `/join/accept` and `/join/confirm` already show, and shows the workspace, the inviter and the proposed roles in plain words ("Viewer in all Spaces", "Approver in Payments"), then one of a password form (an address nobody signs in with yet), "This address already has an ExecBound account. Sign in, then open the link again." (an existing or legacy address, signed out), an **Accept** button for the right account already signed in, or `mismatch` for a different one. **`POST /join/accept`** (new address) takes a password and confirmation, and on success mints a session with `issue_session`/`session_response`; a fault signing that new account in, after its acceptance already committed (`sign_in_invited_account`, guarded the same way `issue_session` already is), answers the same "You have joined. Sign in." page a retried acceptance of an already-accepted link answers too, rather than a bare 500. **`POST /join/confirm`** (signed in) re-authenticates the account cookie and the session inside the accepting transaction before calling `accept_invitation`, behind the ordinary `guards.mutation` CSRF/Origin checks, and shows "You have joined `<workspace>`. Choose it from the workspace menu." for a fresh acceptance, an already-committed retry, or `ALREADY_MEMBER` alike, because all three share the one true fact that the account is a member; a session still waiting for its own MFA is treated as signed out and sent to `/mfa`, never shown the invalid or mismatch page. `FORBIDDEN` (the inviter lost authority) and `INVALID_TENANT` both render the same `invalid` result a forged link does, so a stranger never learns why. Every page is `Cache-Control: no-store` under the site's default `Referrer-Policy: same-origin`, and the exact Origin check applies to both mutation routes (`surfaces/invite_pages.py`, `invitations.py`). See [Threat model](THREAT_MODEL.md) T4.35 to T4.39.

The console API adds `/api/console/v1/teammate-invitations` (list, create, resend, revoke). An invitation is an email, so the session carries `mail`, whether this deployment has a relay at all, and the console offers to invite by email only where it does: without one, the People page says that inviting needs a relay and points at **Add user**, which sends nothing, and the API still records an invitation it is asked for, for a relay added later to deliver. The three tables are kept by hand, so a code added to one needs a matching entry in the other two.

### The live board

The board draws the last fifteen minutes as a board of lanes: agent principals on the left, the checkpoint in the middle, targets on the right, and every shot a row the tenant already holds. It reads the same rows as Home, under the same approver scope, in one `REPEATABLE READ` snapshot sharing one server-fixed instant, and it changes nothing. The console draws it at `/board` from `GET /api/console/v1/board` and its stream. The hosted service renders the same read server-side as a public showcase; that page is documented with the hosted service.

It is the console's one full-ink page, an exception to the console's shared design, because it is a display surface for a wall or a screen share.

Beneath the board, when the tenant has an active monitoring source or connection, a band says "seen by monitoring, not governed": grey shots that pass *under* the checkpoint, because that is what they did, with a finding marking its shot. A directory's own audit log records ExecBound's executions and the attempts it refused too, so an audit-log observation is drawn only when it succeeded and is not the one entry an execution ExecBound settled accounts for, by the same match `first-consequential-action.v1` uses ([Scout](SCOUT.md#what-the-directorys-own-audit-log-shows)). It is drawn for an administrator only. An observation carries no canonical target, so it cannot be held to an approver's scope the way an execution is: showing it unfiltered would hand an approver activity outside the scope they were given, and filtering it by a target label would be a guess. The band is absent entirely when nothing is watching, because an empty band reads as "monitoring saw nothing", which is a stronger claim than "nothing is watching".

Every key here is an HMAC-SHA256 key and is compared as HMAC uses it, so a key with zero bytes appended is the same key for every one of these rules. `notifications` (optional, up to 64) names operator destinations; `kind` is `webhook` (pending-approval notifications, the default), `email` (pending-approval notifications by email), `slack` or `teams` (pending-approval notifications in a channel) or `security-events` (the audit export, see [Operations](OPERATIONS.md#structured-logs-and-security-event-export)). An optional `classes` list says what a destination carries, `approvals` (the default) or `findings` or both, as `soc-slack` carries both above; a findings destination may narrow itself with `rules` and `spaces`, `messages` and `approvers` belong to approvals, and all three are described in [Operations](OPERATIONS.md#send-monitoring-findings-to-destinations). `mail` (optional, required when any email destination exists) is the deployment's one SMTP relay: `host`, `port` (465 or 587), `tls` (`tls` or `starttls`, never plaintext), `username`, `password`, `from` (a bare address) and `daily_limit` (default 500 messages per tenant in any 24 hours); see [Operations](OPERATIONS.md#send-notifications-by-email). Destinations are neither tenant data nor ADMIN-editable, like connector origins. `preconditions` (optional, up to 64) declares what each provider binding's vendor does with a frozen expected version, for the [external execution checkpoint](CHECKPOINT.md). Each entry names a `provider`, a `provider_operation` and a `precondition_class` of `ENFORCED_BY_PROVIDER`, `ASSERTED_BY_EXECUTOR` or `UNAVAILABLE`, and the class travels with every grant for that binding and appears wherever the checkpoint is shown. It is keyed by the binding and never by the account, because a checkpoint account has no connection configuration at all and whether a version can be checked is a property of the vendor's API rather than of one tenant's account. Two operator rules matter more than the shape. **An undeclared binding promises nothing**: it answers `UNAVAILABLE`, its grants carry no expected version, and a deployment with no `preconditions` block issues only `UNAVAILABLE` grants: the honest default, not an oversight. **Declaring a class is a statement about the vendor's API that ExecBound cannot verify**: nothing checks that the vendor really offers a conditional write or really exposes a version, so a class claimed for a vendor nobody checked is an overclaim on every page and every report that shows it. A binding declared twice, or one the running catalog does not bind, is refused at load like any other invalid file, and a reload that finds a changed declaration reports `refused` and leaves the running keys untouched, because that change needs a restart. `checkpoint_providers` (optional, up to 64) declares the journal key each Gate account's provider signs with, for the [checkpoint](CHECKPOINT.md)'s `PROVIDER_VERIFIED` tier. Each entry names a `tenant_id`, an `account_id`, a `provider` and `evidence_keys` (a key id to hex-encoded key, the same shape a connector's own `evidence_keys` take), and holds no URL and no dispatch or control token, because the gateway never calls this provider: verification only. An account named here and also under `connectors` or `graph_connectors` refuses to load, as does a duplicate entry, because a Gate account has no connector by construction and admission's own refusal of a Gate mapping whose account has a connector would otherwise disagree with this file about what kind of account it is. A journal key must be independent of every connector's evidence keys and of the continuation keys, checked at construction and again on `Runtime.rotate`, so the same secret can never verify two different things. **Changing this block is not a key rotation**: it is read once when the runtime is built and carries no rotation of its own, so a reload that finds it changed reports `refused` and leaves the running keys untouched exactly as a changed `preconditions` or `arcade` block does, and the change needs a restart. `arcade` (optional) is the tool map and deadline for the [Arcade logic extension](ARCADE.md), and its presence is also what makes the deployment serve `POST /pre` and `POST /post`. `deadline_seconds` is **required with no default** and at most 30: a default would be a number the deployment inherits silently and could not defend, so a block omitting it is refused at load. `post_bytes` defaults to one MiB. Each entry of `tools` declares one governed tool: exact `versions` with no wildcard, the `operation_ref` it reaches, one `target` input with a `kind` of `canonical`, `hostname` or `provider_id`, an optional `incident` input, the `inputs` allowlist, an `arguments` map into the action's typed arguments, and an optional `expect` that may only deny. `ungoverned_toolkits` names toolkits that pass with no kernel call at all. Three operator rules matter more than the shape. **The `incident` id is a claim the agent supplies, never a fact the platform asserts**: the kernel checks it against the resolved target under the mapping's own tenant, account, provider and resource type, so a claim naming another tenant's incident, another account's or another resource's is refused, and an incident standing against the right target in the wrong state is the tenant's **policy pack** refusing it on the frozen `incident_status` and `incident_severity` facts, not the kernel. A released contract needs the declaration at all: each of the four the production catalog releases sets `incident="required"`. **A precondition class declared for a binding an Arcade deployment serves is an overclaim**, because no version reaches Arcade (the hook response has no field for a grant and the extension sets no override), so declare none for such a binding and accept `UNAVAILABLE`; a binding served through both a Gate story and Arcade has one declaration for both carriers and must take the weaker. **A changed `arcade` block is not a key rotation**: the block is part of the configuration shape, so a reload that finds it changed reports `refused` and leaves the running keys and the running tool map untouched, and the change needs a restart. Beside the refusals every invalid file gets, the block is refused for an `operation_ref` outside the character class `ActionRequest.operation_ref` itself admits, a toolkit named as both governed and ungoverned, a `target.input` or `incident.input` outside its own `inputs`, an argument mapped from an undeclared input, two inputs mapped to one argument, and a duplicate tool declaration; a deployment carrying an `arcade` block may declare no connectors at all. `telemetry` (optional, default off) records whether this deployment would send ExecBound one weekly usage report. It is deployment-wide rather than per tenant, which is why it is here beside the connectors, and `execbound init` asks the question once and writes the answer. **Nothing reads it yet**: no report is composed, no schedule exists and no endpoint receives one, so the block is an answer recorded where the decision lives and not a feature. `console` is accepted and ignored: the console is served whatever it says (see [how the console is served](#how-the-console-is-served)), and a file that still carries the block is named in one `configuration.ignored_block` event rather than refused, so a gateway never fails to start over a file nobody has edited yet. `service` (optional) names where this deployment sends people for help, every field optional: `support_email`, which the MFA pages' "Get account help", the console's Help page and My account write to, and `help_url`, `status_url`, `privacy_url`, `terms_url`, `plans_url`, `security_url` and `privacy_requests_url`, which the page footers, the sign-in page's "Forgot your password or lost access?", the console's Help page and Workspace settings' requests card link to. `source_url` is the footers' Source link, where the code the deployment runs can be read, and the one with a default: the public repository, `https://github.com/ExecBound/execbound`, kept when the block leaves it out. A deployment that runs changed code names its own copy, which helps it meet the AGPL's network clause, and `null` hides the link. `operator` names who runs the deployment, at most 80 letters, digits, spaces and `.,&'()-`: the footers show "© 2026 \<operator\>" when it is set and "Powered by ExecBound" when it is not. Any other link with no address is not shown, so a deployment without the block shows Source alone. Each URL is `https://` with a host, no user information and at most 200 characters, and the address is one `@` between a local part and a domain; anything else, or an unknown field, refuses the file. A loaded plugin may give these instead, and a file with the block beside such a plugin is refused at start. A changed `service` block is not a key rotation: a reload that finds it changed reports `refused`, and the change needs a restart. `plugins` (optional, up to 8) names the first-party plugins this gateway loads, each with its own section, which that plugin validates; a self-hosted gateway needs none ([Without a plugin](#without-a-plugin)). A changed `plugins` block is not a key rotation: a reload that finds it changed reports `refused`, and the change needs a restart. `key_reload_seconds` (0 to 3600, default 0) makes the gateway re-read the file at that interval and rotate the key rings when only they changed; see [Operations](OPERATIONS.md#rotate-signing-and-evidence-keys). The configured origin controls Host/Origin validation and the fixed approval URL. Run the separately configured mock using [PROVIDER.md](PROVIDER.md).

Existing endpoint configurations may omit `provider`; its default remains `mock_crowdstrike`. An identity connector must explicitly use `mock_entra` with its separate account, credentials, signing keys and provider process. See [IDENTITY_PROVIDER.md](IDENTITY_PROVIDER.md). Human lists, decisions and rendered action names use the frozen canonical action; an assignment for disable cannot approve enable or revoke sessions.

`sample_providers` (optional) serves [sample targets](ACCEPTANCE_TESTS.md#sample-targets-sm1-to-sm11). It is keyed by provider, and this release accepts only `mock_crowdstrike`. Each entry names the mock's `origin`, which obeys the rules a connector's origin obeys, a `sample_key` of 32 to 128 random bytes written as lower-case hex, and `timeout_seconds` (default 5, at most 30). For an account whose row is active and marked `sample`, which only the `samples_install` function can mark, the gateway derives the dispatch token, the control token and the journal key from the sample key, the tenant and the account, builds the connector when a request needs it and closes it afterwards; an account that is not marked `sample` never gets one, and a configured connector resolves exactly as before. A sample dispatch records `ENFORCED_BY_PROVIDER` only when the `preconditions` block beside this one also declares `mock_crowdstrike`'s `contain` and `lift_containment` that way, exactly as `bootstrap.MOCK_PRECONDITIONS` does for this deployment; with no such declaration a sample dispatch answers `UNAVAILABLE` like any other undeclared binding. The endpoint mock holds the same key as `EXECBOUND_MOCK_SAMPLE_KEY` ([PROVIDER.md](PROVIDER.md#sample-accounts)). The key must differ from every connector evidence key, continuation key and checkpoint journal key, compared as HMAC-SHA256 uses a key, and may not be a published test key, checked at start and on every rotation. **Changing this block is not a key rotation**: a reload that finds it changed reports `refused`, the change needs a restart, and a new key cuts every workspace's sample connection until the mock holds the same key. Containment is per tenant: the mock refuses a sample token for any tenant it already holds a configured account for, whatever account id the command names, and `samples_install` refuses a workspace that already holds an active connector account, so a sample account can exist only in a workspace with none. The gateway mirrors the mock: in a tenant this file holds a connector for, it derives no sample connection and offers no samples, even where a sample account remains because the slot was switched off in the database but not here, so a sample request there is refused at admission instead of being sent to a 401 and left `INDETERMINATE`. Whoever holds the key can act on every workspace's sample endpoint mock and on nothing else ([Threat model](THREAT_MODEL.md) T3.9, R28).

## Rules

`/policy/{bundle_id}/rules` is the ADMIN editor for rulesets. It is a console page over `GET` and `POST /api/console/v1/policy/{bundle_id}/rules`, described [below](#how-the-console-is-served): the rules apply to the actions the draft's mappings serve, the form offers only the facts, arguments and values those actions' contracts declare, and each change writes a successor draft and retires the one it replaced. A rule is compiled with the draft before it is accepted, so an unknown fact or a value outside its domain is refused with its location at the form, not only at validation. Creating the draft goes through `ruleset_bundle()` and the store, so the page never writes a component and the store's mismatch check is the safety property. The bundle page shows a ruleset bundle's rules as sentences, its notes as text, the compiled Cedar read only, and names the rule beside each preview change and each quorum obligation. An approver is refused with 403. The audit chain carries `policy.ruleset_compiled` beside `policy.bundle_created`, with counts and never the rules' text. A ruleset bundle's rules also download as the file `ruleset-compile` reads, and such a file starts a draft in another workspace (below).

Other pages read the rules too. The agent page carries a Rules column beside each governed action, the rules about that action in the compiler's order. Every reading is labelled as a reading ("Rules are as they read for the action; the decision is the kernel's, from the compiled bundle."), and `tests/test_pack_rulesets.py` proves the reading equal to the kernel's policy decision over the whole input space of every pack, `tests/test_rule_reading_operators.py` over the operators the packs do not write; a bundle written as a document adds no Rules column and no claim. `/policy/rules` redirects to `/policy`, where Customize current protections copies the active bundle, its rules included, into a draft (`POST /api/console/v1/policy` with `{"source": "active"}`).

## How the console is served

The console is a single-page application. It is not optional and has no flag: a deployment whose private configuration still carries a `console` block has it accepted, ignored and named in one `configuration.ignored_block` event, so a gateway never refuses to start over a file a person has not edited yet.

Each of the console's routes serves the application's one document to a signed-in person: a visit with no session or an ended one is sent to `/login`; a bearer credential is refused with 403 and audited as `execution.rejected`, as on every page; a duplicated query key is refused, and every other key is the application's own state, which the server never reads. The document is `no-store` and carries the running commit in `<meta name="execbound-release">`, so the client can tell a release it was not built for. `GET /console/{file}` serves the build's own files: the hashed ones under `assets/` as `public, max-age=31536000, immutable`, the rest the build ships (the token stylesheet, the plain frame, the fonts) revalidating by `ETag`; build metadata and any file of a type the server does not know are not served, and the document is never one of them.

Every console route and every `/api/console/` response carries the console's policy: `default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' data:; font-src 'self'; connect-src 'self'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'; require-trusted-types-for 'script'; trusted-types 'none'`. It is chosen by matching the console's own route list rather than by a path prefix, because the console and the pages that stay now share the address space: `/approvals/{id}` is the application and `/approvals/{id}/classic` is the page behind it. Every other response keeps the pages' policy, which allows `font-src 'self'` so those pages can take the packaged IBM Plex, and `img-src 'self'` so the mark every page links is not refused by its own `default-src 'none'`. A package that carries no build answers 503 with a plain sentence on every console route, so a missing build is never mistaken for a path that does not exist; the pages that stay answer as they always did. The build itself is produced by `console/` (Vite, React 19, TypeScript, pnpm 11 under the supply-chain settings `console/DEPENDENCIES.md` records) and written into the package; `tests/test_console_serving.py`, `tests/test_console_dependencies.py` and `tests/test_route_authority.py` hold the behaviour above.

**Editions**. The console is built from one source tree. The core edition, `pnpm build` (`vite build`), is what the package, the wheel and the self-hosted image carry; a plugin's console edition is built from the same tree with its own directory added, and an image built with another `CONSOLE_EDITION` ([Deployment](DEPLOYMENT.md)) carries that build instead. Core's pages read what an edition adds through slots, one React context (`console/src/edition/context.ts`) whose default is the core edition, where every slot is empty: `navigation`, entries in the sidebar, the phone's tab bar, the palette and the breadcrumbs, after core's main entries and before the footer entries, and in the sidebar within the group each names; `TopBarItems`, among the top bar's actions, after the mode and the emergency stop and before Ask; `paletteLinks`, server pages in the command palette's own "Actions" group, before "Go to", each offered only where the session's `features` hold its own feature; `WorkspacePanels`, cards after the data and closure requests on Workspace settings; `TenantDefinitions`, definitions after the active bundle in Workspace settings' "What this tenant is"; `AccountPanels`, cards between the profile and the data requests on My account; `Welcome`, the end of Getting started, after its steps; `FixtureHint`, the example request's target on "Connect this agent" where core names no workstation; `ApprovalRemedy`, the sentence after Workspace settings' approval readiness warning, `null` in core, which keeps core's own sentence; and `event`, which core calls when something countable happens and which counts nothing in core. Two flat flags say what setup may offer, each a top-level `boolean` and neither wrapped in an object: `operatorCommands`, whether the people reading the console also run this deployment's operator commands, so Monitoring and Getting started may show them; and `watchFirst`, whether an administrator can connect a monitoring source by following the console's own setup dialog, so Getting started and Home may offer watching first. Both are `true` in core. The hosted service's console edition fills them; what it adds is documented with the hosted service. Only `console/src/main.tsx` imports the two aliases that choose an edition, `@edition` for the slots and `@route-tree` for the routes, and it provides the edition around the router. The core build lists every module it loaded and fails if one lies under `console/src/hosted/` (`console/scripts/editions.ts`), and ESLint refuses an import of a hosted module, static or lazy, in every core file under `console/src/` and `console/scripts/`, and either alias in any of those core files but `src/main.tsx` (`console/eslint.config.js`). The server lists core's pages in `CONSOLE_ROUTES`. A plugin registers its own console pages with `registry.console_path`, and the workspace-scoped approval addresses, the console's `/workspaces/{tenant_id}/approvals/{approval_id}` and the classic `/workspaces/{tenant_id}/approvals/{approval_id}/classic`, are mounted only where a loaded plugin registered approval links; without such a plugin each answers 404 under the pages' policy. `/health/ready` reports `"console": "<edition>"`, the edition the served build names in its document, read once when the application is built, in a process that serves the console; it reports the edition and refuses nothing over it. `tests/test_console_serving.py` holds the behaviour above, with CE1 to CE15 in [the acceptance inventory](ACCEPTANCE_TESTS.md#console-editions-ce1-to-ce15).

The console API lives under `/api/console/v1/`. It answers **two callers**: a signed-in person's session, and an administrator's own personal access token, `Authorization: Bearer ebp1.<tenant>.<token>.<secret>`, minted from **My account → Personal access tokens** and shown once. Minting one steps up any second factor the administrator has enrolled (`require_recent_factor` is a no-op with none enrolled, so an administrator without one is not asked for one). Every route runs the pages' own boundary regardless of which caller it is (the query allowlist, the Host pin, the identity-header refusal), any other bearer credential (an agent's `eb1` key among them) refused with 403 and audited as `execution.rejected`. A session request loads the session from its cookie, checks the CSRF cookie, and additionally needs, on a mutation, `Content-Type: application/json`, a body of at most 64 KB with no duplicate key and no field its model does not declare, and an `X-CSRF-Token` header equal to the session's token, a mismatch being audited as `INVALID_CSRF`; the exact Origin check and the workspace-generation header are the pages' own. A token request skips the Origin check, CSRF and the workspace-generation header, because they defend a cookie a browser sends on its own and a session that can switch workspace, and a token is neither; it keeps the body rules above, is looked up by its own transaction and rechecked as a session-shaped authority (`personal_tokens.TokenSession`), and must name a route `token_rules.token_allowed` admits, from core's own table or, for a loaded plugin's own console routes, that plugin's classification (`token_routes`), or is refused 403 `TOKEN_NOT_ALLOWED`, audited. A token has its own 300-request-a-minute rate limit, may name a space with `X-ExecBound-Space` (unscoped, it sees every space its owner can), and is refused with `DIRECTORY_REQUIRED` in a workspace that requires sign-in through an identity provider; a request carrying both a session cookie and a bearer token is refused rather than resolving one. A refusal is JSON, `{"code": ..., "detail": ...}`, from a closed list of codes the generated client maps to copy, and it is JSON to a browser too: the HTML error pages never answer on this prefix. `tests/test_console_api_tokens.py`, `tests/test_route_authority.py` and `tests/test_personal_tokens.py` hold the token half of this boundary; PT1 to PT13 in [the acceptance inventory](ACCEPTANCE_TESTS.md#personal-access-tokens-pt1-to-pt13). Every response carries `X-ExecBound-Release`, the running commit, so the client can tell a release it was not built for. `GET /api/console/v1/session` returns the signed-in person (principal, kind, label), the tenant (name, mode, approval deadline), the tenant's active emergency stop (id, when, by whom, the reason) or null, read as the pages read it for their banner so the console shows the same banner on every route and an approver sees the state, the session's expiry and its hard end (`ends_at`, eight hours after signing in or the credential's own expiry when that is sooner, which no renewal moves, and `end_reason`, `sign_in` or `setup_credential` for a session a setup credential opened that ends on it), the release and the CSRF token, which is the one place the token leaves the server as data, under `Cache-Control: no-store`. It also carries `invitations`, whether the session feature of that name holds, and `features`, the sorted names of every loaded plugin's session feature that holds for this session, `invitations` among them where it holds, which is `[]` without a plugin; a plugin's console edition reads its own names from that list. It carries `service` too, the deployment's service links with each of its eight fields `null` where the deployment names none ([configuration](#private-configuration-and-startup)), which the console's Help page, footer, My account and requests card read. `POST /api/console/v1/client-errors` takes `{route, release, name, stack_hash}` of bounded shapes, never a message text, and writes one `console.client_error` log event; the console's route boundary sends one for a page that fails other than by a typed refusal (below, **The console's shell**). The committed OpenAPI document, `console/openapi/console-v1.json`, holds core's areas only and is the published one, and the client at `console/src/api` is generated from it. A plugin's console areas have their own document, `console/src/<plugin>/openapi/console-<plugin>-v1.json`, from which that plugin's console edition generates its own client. `uv run python scripts/console_openapi.py --plugin <plugin>` writes both, and `--check` compares both; `tests/test_console_api_base.py` holds core's equal to what the router builds, and the `console` CI job generates both clients from them. `tests/test_console_api_base.py` and `tests/console_api_fixtures.py` hold the behaviour above and are the harness every area's routes reuse.

A ticker row does not yet open its record, because the drawer's search parameter belongs to Activity's route; the card links Activity instead. `tests/test_browser_console_board.py` holds the behaviour above in Chromium and `console/src/components/board/board.test.tsx` holds the geometry, the counters, the ticker and the stream hook. `tests/test_browser_console_soak.py` leaves the board open with the stream sending, and holds the JavaScript heap to less than twenty per cent growth since a fifth of the way in while counting the frames that actually arrived, then hides the tab and holds it to no request and no frame at all; `EXECBOUND_BOARD_SOAK_MINUTES` sets its length and Home's, three minutes by default and ten for the full ten-minute soak.

### Without a plugin

A deployment whose `plugins` map names no plugin runs the self-hosted core, which is what this page describes. The hosted service's plugin adds routes, pages, commands and console cards of its own, documented with the hosted service. In the core:

- the page footers' Help, Privacy and Terms, the console footer's Privacy, Terms and Status, the account-help links and `GET /api/console/v1/session` `service` come from the runtime configuration's `service` block, and without one none of them is shown; the footers' Source link and `source_url` name the public repository unless that block names another address or `null`, and the footers credit the software ("Powered by ExecBound") unless the block names an `operator`;
- the runtime role holds nothing on the dormant tables and functions ([Data model](DATA_MODEL.md#roles-and-connection-behavior)), and a database that grants it anything is refused (`/health/ready` answers 503);
- a command on the runtime connection other than `quickstart`, or `/health/ready`, against a database holding grants for a plugin the process has not loaded exits 2 with the sentence naming `EXECBOUND_PLUGINS`, or answers 503;
- keys the runtime configuration's schema does not declare are refused as unknown;
- workspace switching (`can_switch_workspaces`, `GET /api/console/v1/session/workspaces`, `POST /api/console/v1/session/workspace`) and the sample target routes are core's own.

## The console's assistant

`/api/console/v1/assistant` is the server side of the console's assistant, with the panel and its Explain entry points. **The addresses exist only where the private configuration carries an `assistant` block**: a deployment that configured no model serves none of them and answers 404 because the path does not exist, exactly as `/` does without the console. Where the block is present, a tenant whose ADMIN has not turned the assistant on is refused `ASSISTANT_OFF`.

`POST /assistant/turns` creates one turn and answers with it at once, as it starts; the model loop runs behind the response in this process, writing each step to the turn's row. The body is a `question` of up to 1,000 characters, or a `context_kind` and `context_id` naming a record to explain (an execution, an approval, a finding, an agent or a policy change), or both; a contextual turn re-reads that record with the asking person's own authority before the model sees anything, so an id the person cannot read is refused as the page refuses it. `GET /assistant/turns` lists that person's recent turns and `GET /assistant/turns/{turn_id}` reads one: **their own only**, so an administrator cannot open an approver's question. `GET /assistant/turns/{turn_id}/events` follows a turn as server-sent events, one `step` event per step the row gains and one `done` event carrying the finished turn, closing when the turn ends or at ninety seconds; it reads the row and nothing else, so a restart mid-turn, a second gateway process or a person opening the page late all see what the row says. `POST /assistant/turns/{turn_id}/opened` records that a person opened a generated explanation, appended as `assistant.explained`, so a later review can see which decisions were made after reading one. `GET` and `POST /assistant/settings` are the ADMIN's: the tenant switch with a required reason, audited as `tenant.assistant_changed`, answered with the model's name, the caps and one sentence naming what the provider retains.

`POST /assistant/rules` drafts one rule for a draft from an administrator's own words and writes nothing: it answers with the rule as the add-a-rule form takes it, its sentence, and its conditions in the words the editor parses, having already compiled it with that draft's other rules against that draft's mappings. A proposal the compiler will not take, or one holding text shaped like a credential, answers `INVALID_PROPOSAL` naming the field and never the text: its id is written into the audit chain, and the event export refuses a window holding such text for good. Only a DRAFT written as rules can be drafted into; anything else is refused as the rules page refuses it.

Every answer the console renders is plain text with no markup, and a citation is a link only to an id a tool returned in the same turn. The engine behind these routes is `execbound/assistant/`, described in [Policy](POLICY.md#rules); nothing it does reaches a provider or writes anything but the turn's own row.

`/ask` and `/ask/{turn_id}` are the console side of those routes. **The entry exists only where the operator's `assistant` block does**: `GET /api/console/v1/session` carries `assistant`, so the shell knows before it paints and a console built for a deployment without one shows no navigation entry, no top bar button, no palette group and no Explain, and `/ask` is the shell's own not-found. Below 1280 px the top bar's Ask button shows its icon alone and keeps its name as its label; up to 480 px wide, and below 560 px wherever an edition's action marked the same way sits beside it, the top bar leaves Ask out and Menu's navigation sheet carries Ask instead, so the bar fits beside a second workspace's chip. Whether the tenant turned it on is `GET /assistant/settings`, which is an administrator's route, so an administrator is told before they type and offered the way to Workspace settings, while an approver simply asks and is refused `ASSISTANT_OFF` if the switch is off. Ask is a question box and the asking person's own recent turns, which are theirs alone: an administrator's list holds their own questions and nobody else's. A question answers with a turn and the page goes to `/ask/{turn_id}`, where the steps arrive over the events stream as the server takes them, then the answer. An answer is paragraphs of plain text with a chip for each id a tool returned; the server says which ids those are and not what kind of record each names, so a chip is a link only for the turn's own context, whose kind the turn states, and inert text otherwise. The command palette's Ask group carries the typed words to `/ask?q=`, where the person reads them back and presses Ask: the palette never asks anything itself. `Explain` sits below a record's own facts, collapsed, labelled "Generated explanation. The facts above are the record."; opening it creates the turn and records `recordAssistantTurnOpened`, and it is on the approval detail, the activity drawer, a policy preview's changed decisions, the agent detail page and each monitoring finding. Workspace settings gains the Assistant card: the switch over `/assistant/settings`, which only a workspace administrator may turn (`set_tenant_switch` refuses an administrator narrowed to spaces `INVALID_IDENTITY` and the route answers 403; they read the switch, and the card offers them no button), what the assistant is and is not, and the sentence naming what the model provider keeps, stated again in the dialog that turns it on with its recorded reason. `console/src/components/assistant/*`, `tests/test_browser_console.py` and `console/src/components/assistant/assistant.test.tsx` hold the behaviour above.

"Describe a rule" is that route's console side, on `/policy/{bundle_id}/rules` above the add-a-rule form. An administrator says what the rule should do; what comes back fills the form beside the words that produced it, with the sentence it reads as and its conditions in the words the editor parses, and every field stays theirs to edit. The card is absent where the operator configured no model, hidden where the tenant has not turned the assistant on, and hidden on a bundle that cannot be edited. **Nothing is added to the draft by describing one**: the rule reaches the draft only when the person presses Add the rule, which is the same submission as any other, and a proposal the compiler would not take is refused before it reaches the form with one sentence saying what to say instead. `console/src/components/assistant/DescribeRule.tsx` and the Chromium walk in `tests/test_browser_console.py` hold the behaviour above.
